# BYOK（用户自带大模型）方案讨论

> 记录关于「普通用户如何接入自己的大模型」的讨论与技术选型，供后续跟进。

## 背景 / 现状

当前模型与密钥是**服务端全局配置**，只有部署方能改，普通用户无法通过界面接入自己的模型。

配置入口在 `config.py`，启动时从环境变量读取，对所有用户生效：

| 变量 | 作用 |
|---|---|
| `ARK_API_KEY` | 火山引擎 ARK 密钥（必填） |
| `ARK_BASE_URL` | API 地址，默认火山 ARK（`https://ark.cn-beijing.volces.com/api/v3`） |
| `DOUBAO_MODEL` | 模型名，默认 `doubao-seedream-5-0-260128` |

前端（`useSession.ts` / `api.ts`）不会携带用户自己的密钥。要「接入自己的大模型」目前只能由部署方改 `.env` 后重启后端。

若要支持**终端用户自带 key/模型（BYOK）**，需要新增：设置界面 → 传递密钥 → 后端按请求/会话覆盖 `DoubaoConfig`（而非全局单例 `config`）。

## 关键安全原则

> **密钥永远不进浏览器持久层（localStorage）。**

- localStorage 明文存储、可被任意 JS（含 XSS）读取、无过期，**不适合存密钥**。
- 主流做法二选一：
  1. **Provider OAuth**：前端从不接触原始 key，只拿短期 token（最佳）。
  2. **后端托管密钥**：key POST 给后端，服务端存储，前端只保留会话令牌。

## 参考：主流工具怎么做的

### opencode CLI / `opencode web` / 桌面端 —— 本地优先

opencode 的核心是操作**本地文件与 shell**，agent 必须跑在用户自己机器上。`opencode web` 起的是 `127.0.0.1` 本地服务，浏览器只是壳。因此 key 直接落本地文件 `~/.local/share/opencode/auth.json`，opencode 云端从不接收。

> 这套依赖「后端 = 用户自己的机器」，**无法照搬**到真正托管的 Web 应用。

### OpenCode Zen 控制台（`opencode.ai/auth`）—— 托管网关 + 后端加密托管

这是一个**真正托管的多租户 Web 应用**，其 BYOK 流程：

1. **登录 = 建认证会话**：账号系统发 session token/cookie。
2. **填 key = 表单 HTTPS POST 到后端**，只传一次，不进浏览器持久层。
3. **后端加密存储**：key 存服务端，绑定账号/workspace，静态加密。
4. **后端代理调用**：Zen 是 AI 网关，请求打到 Zen → Zen 用你的 key 调 OpenAI/Anthropic → 计费直接走 provider。
5. **前端只回显掩码**：如 `sk-...abc4` + 轮换/删除按钮，拿不到明文。

## 两个候选方案

两者**共同点**：key 交后端、前端只留会话凭证、后端代理调用，浏览器都不持久化明文 key。
**区别**只在「存多久 + 要不要账号体系」。

### 方案 1：会话内存（轻量版，推荐先做）

- key 在「设置」时 POST 给后端一次，存在后端**会话内存**（`MemoryStore`），绑定匿名 `session_id`。
- 前端只保存 `session_id`，永远不持有 key。
- 刷新 / 重启 / 会话过期即失效，用户需重填。

### 方案 2：账号 + 加密持久化（Zen 同款，产品版）

- 需要完整**登录/鉴权系统**。
- key 加密存**数据库**，绑定账号/workspace，静态加密。
- 一次录入长期有效、跨设备。
- 需额外承担：加密/KMS、密钥轮换与删除 UI、泄露责任、合规。

### 对比表

| | 方案 1（会话内存） | 方案 2（账号 + 加密持久化） |
|---|---|---|
| 存哪 | 后端**内存**（`MemoryStore`） | 后端**数据库**，静态加密 |
| 绑定谁 | 匿名 `session_id` | 真实账号 / workspace |
| 要登录吗 | 不需要 | 需要完整鉴权系统 |
| 存多久 | 刷新/重启/过期就没了 | 一次录入，长期有效，跨设备 |
| 用户体验 | 每次（或重启后）要重填 | 填一次，永久可用 |
| 需承担 | 几乎为零（不落盘） | 加密/KMS、轮换删除、泄露责任、合规 |
| 工作量 | 小，几十行 | 大，是完整产品功能 |

## 选型结论 / 建议路线

- 项目当前**尚无账号系统**，只有匿名 `session_id`。
- 务实路线：**先上方案 1 跑通 BYOK**，等有了账号体系再平滑升级到方案 2。
- 能做 Provider OAuth 时优先 OAuth（前端不碰原始 key）。
